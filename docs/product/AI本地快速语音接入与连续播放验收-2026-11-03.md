# AI 本地快速语音接入与连续播放验收

日期：2026-11-03。范围：speech60–65，分支 `codex/ai-web-sources`。

## 已确认范围

- AI 中文语音采用 Matcha zh-en 候选的单一基础音色；AI 其他语言继续现有 Supertonic 路线。
- 普通翻译、面对面翻译保持原 TTS 路线和保存的音色设置。不会将 AI 专用 provider 写回全局设置。
- ASR 保留 Whisper base int8。前一阶段 Qwen3-ASR 对照尚不足以证明替换后的整体收益。
- 本轮不需要云端语音服务，不进行真实外部模型 API 测试，不推送 GitHub 或公开发布。

## 变更

1. 加入内置 Matcha 资源存储、校验与原子准备；AI 预热、预合成、朗读使用一致的中文引擎。
2. 模型归档使用 gzip，避免 bz2 在手机上长时间准备。首次准备仍有开销；已加载同一引擎时，不再逐段重复检查362个资源文件。
3. AI 从翻译页面返回后刷新预热状态，防止把旧预热时间当成新引擎仍驻留。
4. 同一回答继续使用同一 AudioTrack group，16kHz Matcha PCM 通过既有流式重采样进入44.1kHz输出。
5. PCM队列达到1MiB后施加背压，降到512KiB时恢复接收，给后续合成保留音频余量；停止和错误关闭旧队列的等待确认。

## 排查中纠正的判断

preview62/63只观察10秒时，未见第二段 `buffered` 日志，一度怀疑缓存队列卡死。preview64延长到45秒后确认已推进7次请求，因此不能据此称卡死。

真实瓶颈是原实现越过高水位后，要等该append在writer队尾全部写完才回确认，后续合成可能等到队列接近耗空才开始。preview65改变确认时机，保留最终writer排空与playback head尾音保护。

## 真机证据与边界

OPPO PEHM00，Android12；只查看既有测试回答和运行状态，没有在此轮开启麦克风。

- preview61新中文合成多段约RTF0.14–0.18；这些是生成耗时，不是扬声器首响。
- preview62 gzip首次资源/worker准备约9秒，相比此前bz2约48秒；这是候选包的单机观察，不是跨设备保证。
- preview62普通翻译“Good morning”得到“早上好”，朗读仍由原Melo路线处理。
- preview64长回答45秒观察确认队列继续推进，纠正卡死推断。
- preview65既有长回答的34段全部入队并自然完成，包含中文和独立英文片段。最终音频272,672ms，播放器建立到结束272,844ms，相差172ms；收到了group级`tts_done`，队列为0。脚本含轮询和收尾的总运行时间281.69秒，不能拿它代替播放器时间。
- 最终`underruns=1`，不是零欠载；这次数据支持没有多秒累计供给等待，不能代替听感评估或定位欠载发生时刻。
- 同一Matcha worker后续多段`workerReadyMs=0`，证明已加载引擎不再逐段重走资源检查。
- 停止复测：播放8秒后点停止，原group收到`tts_stopped`，JS清空队列；等待3秒没有自行续播。再次点朗读后，播放3秒切换到翻译页，第二个group同样停止；随后5秒没有新播放请求。截图核对已回翻译页。仅证明这次操作路径和观测窗口，不代表所有设备听感已验收。

日志与包校验材料位于 `output/speech60/`，不作为公共源码提交。不得把首PCM写入时间称为真实听到声音的时间。
